# Livraison comptes clients et e-mails — 21 octobre 2026

Le code est prêt pour une livraison coordonnée. Les tests locaux ne confirment pas l’envoi par le vrai compte Gmail ni l’état du VPS. Les clients sont distincts des comptes administrateurs ; WhatsApp reste le canal de conversation.

1. Vérifier une sauvegarde PostgreSQL récente hors VPS et sa procédure de restauration. Conserver Neon. Si AutoDeploy est actif, le désactiver sur les deux applications avant de mettre leur branche de production à jour.
2. Préparer la connexion de migration privée **gainde_owner**, sur le même service/base/schéma. Conserver `DATABASE_URL` avec **gainde_app** pour le fonctionnement normal. Ne jamais partager ces valeurs dans le chat ou une capture publique.
3. Depuis une copie de ce code ayant les quatre migrations, exécuter `npm run db:migrate` avec `DIRECT_URL` privé réservé au rôle de migration. Cette commande doit accéder au réseau privé PostgreSQL du VPS (hôte interne `gaindesportif-postgres-uxa2ed`, port 5432, base `gaindesportif`, schéma `gainde_v1`). Elle n’est pas exécutable depuis un ordinateur extérieur sans accès privé. Aucun `db push` ou `migrate reset`.
4. Les deux premières migrations sont historiques et inchangées. Les deux nouvelles sont `20261021210000_customer_accounts` et `20261021223000_customer_email_notifications`. La seconde remplace le code de récupération, ajoute la vérification e-mail et le suivi. Aucun compte client de production n’a encore été créé par cette extension.
5. Vérifier sur les sept tables clientes les droits DML de `gainde_app`, SELECT seul de `gainde_backup` et interdictions DDL/écriture `_prisma_migrations`. Les privilèges par défaut doivent appartenir au rôle qui crée effectivement les tables. `npm run db:status` doit confirmer les quatre migrations appliquées.
6. Backend Dokploy → Environment : ajouter toutes les variables SMTP/MAIL/CUSTOMER_SITE_URL documentées dans `.env.example`, à partir des valeurs privées. Générer une seule clé de chiffrement 32 octets/base64 et la conserver en privé pour les redémarrages. Le mot de passe d’application Google est créé dans le navigateur du compte expéditeur, avec la validation en deux étapes. Il ne doit jamais être placé dans Git ni le frontend.
7. Mettre à jour/déployer le **Backend**, puis vérifier `/api/v1/health/ready`. Tester l’authentification SMTP avec `npm run mail:check` depuis le code source de la livraison ; l’image runtime ne contient pas le script TS de développement. Un test `--send-self` est réservé à l’adresse expéditrice ; vérifier aussi sa réception dans Gmail. Si aucun accès général au VPS n’est disponible, guider ces étapes dans le terminal privé approprié.
8. Mettre à jour/déployer le **Frontend** après readiness backend. Conserver `BACKEND_URL` privé et `NEXT_PUBLIC_SITE_URL=https://gaindesportif.com`. Aucune variable SMTP dans cette application. Ne pas modifier le domaine ni les réglages Cloudinary.
9. Recetter avec un compte technique identifié : inscription, lien reçu et confirmation, récupération et révocation des sessions, favoris, historique, demande WhatsApp sans envoi, statut renseigné volontairement dans l’administration et réception de l’e-mail. Supprimer uniquement les données de recette autorisées. Vérifier ordinateur/mobile, clavier, réseau et PWA.
10. Lancer/vérifier une sauvegarde incluant les sept tables clientes et une restauration isolée. Conserver les preuves datées dans le contexte parent. Le statut SMTP « accepté » ne garantit pas la boîte principale du destinataire.

**Boutons Dokploy :** les applications Backend puis Frontend nécessitent une publication après migration/configuration. Le service PostgreSQL et le service Sauvegardes PostgreSQL n’ont pas besoin d’un nouveau Deploy pour cette extension. La migration modifie le schéma de la base déjà en fonctionnement. Ne pas cliquer avant d’avoir préparé les étapes 1 à 6.

L’acceptation du manager et les tests sur vrais téléphones restent distincts de la recette technique locale et de la publication.
