# Livraison des comptes clients sans envoi d’e-mail — 21 octobre 2026

L’utilisateur reporte les e-mails jusqu’au choix et à la configuration d’un fournisseur. Les comptes, favoris, historiques et demandes WhatsApp restent disponibles. Les statuts réception/expédition/livraison sont confirmés manuellement par l’équipe et visibles dans le compte. Aucun paiement, transporteur ou API WhatsApp n’est ajouté.

La branche `livraison/comptes-clients-emails-20261021` porte cette livraison. **AutoDeploy reste activé à la demande de l’utilisateur. Les migrations doivent donc précéder la fusion sur main.** Les tests locaux ne prouvent pas que le VPS a été mis à jour.

1. Vérifier une sauvegarde PostgreSQL récente hors VPS et sa procédure de restauration. Préserver Neon et les autres applications.
2. Backend Dokploy → Environment : conserver DATABASE_URL avec le rôle limité gainde_app ; ajouter `MAIL_ENABLED=false`. Aucune valeur SMTP n’est nécessaire. Si un autre réglage y figure déjà, ne pas effacer la configuration de la base, Cloudinary ou du proxy. Ne pas encore déployer les nouvelles applications.
3. Ouvrir **l’ancien Backend → General → Open Terminal**, sélectionner son conteneur actif puis `/bin/sh`. Ce conteneur possède déjà Node, pg et Prisma : il peut joindre le PostgreSQL interne. Le terminal du conteneur PostgreSQL ne possède pas ces outils Node.
4. Exécuter la commande de migration fournie dans le kit de livraison parent après lecture. Elle télécharge `scripts/migrate-customer-release.mjs` depuis un commit immuable et vérifie son empreinte. Le mot de passe **gainde_owner** est saisi uniquement dans le terminal, sans affichage ni historique. Ne pas utiliser le mot de passe client/admin du site ou celui de Gmail ; ne jamais transmettre cette valeur dans le chat/capture. Le script vérifie l’hôte, la base, l’historique et les empreintes des SQL, applique Prisma puis accorde et contrôle les droits.
5. Le résultat attendu est `MIGRATIONS_CLIENTS_OK` : quatre migrations appliquées, sept tables clientes, droits DML gainde_app et SELECT seul gainde_backup, DDL et modification de l’historique interdits pour l’application. Tout autre résultat bloque la fusion : lire le diagnostic, ne jamais utiliser db push/reset ni modifier les anciens SQL.
6. Les deux migrations historiques restent inchangées ; les deux nouvelles sont `20261021210000_customer_accounts` et `20261021223000_customer_email_notifications`. La seconde prépare les fonctions e-mail futures même si l’envoi est actuellement désactivé. Aucun compte client de production créé par la recette locale.
7. Après confirmation de la migration, fusionner/pousser main backend puis attendre sa CI et sa disponibilité `/api/v1/health/ready`. AutoDeploy doit publier cette version. Vérifier `GET /api/v1/customer/config` : `{emailEnabled:false}`.
8. Fusionner/pousser ensuite main frontend et vérifier sa publication. Conserver BACKEND_URL privé et NEXT_PUBLIC_SITE_URL. Aucun réglage SMTP dans le frontend ni changement du domaine/Cloudinary.
9. Recetter ordinateur/mobile, clavier, réseau, PWA : compte technique, inscription sans faux message envoyé, connexion, profil, favoris, historiques, demande WhatsApp sans envoyer de message, statut manuel visible dans le compte, changement de mot de passe et suppression. Les actions d’e-mail restent masquées ; l’accès direct à la récupération indique son indisponibilité. Vérifier que la file et les jetons restent vides pour la recette sans mail.
10. Contrôler une sauvegarde incluant les sept tables et une restauration isolée. Distinguer tests locaux, publication VPS et acceptation manager/vrais téléphones.

**Boutons Dokploy :** aucun Deploy PostgreSQL ou Sauvegardes PostgreSQL nécessaire pour cette extension. Backend puis Frontend sont publiés par AutoDeploy après push main ; un Deploy manuel n’est utile que si ce déclenchement n’a pas eu lieu, après vérification. Ne pas fusionner/pousser main tant que les migrations de la base active ne sont pas confirmées.

## Activation future des e-mails

`MAIL_ENABLED` vaut false par défaut, même si des variables SMTP sont présentes. Aucun message n’est créé, traité ou envoyé dans ce mode ; aucune rétro-notification des anciens statuts n’est prévue. L’achat d’une adresse ne suffit pas à activer l’envoi. Après le choix du fournisseur, adapter/valider sa configuration (l’implémentation actuelle accepte Gmail), renseigner les secrets uniquement backend, conserver une clé AES-256-GCM stable, tester l’authentification et la réception avant `MAIL_ENABLED=true`. Ne pas utiliser le mot de passe habituel du compte ni exposer les secrets dans Git ou le frontend.
